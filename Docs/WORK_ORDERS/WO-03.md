# WO-03 — Node host, Plan page, 2D Site page, facilitator page, Playwright e2e

## Goal

`npm --prefix Monitor run host -- Data/Scenarios/stage1_texas.json` starts one process that owns a `createSim` instance, paces it by wall clock (5 s per day, 20 s per day while `slow`), serves three single-file pages over HTTP and speaks `Docs/PROTOCOL.md` over WebSocket on port 7331. Three people on three laptops (or one laptop and a phone) can play Stage 1 end to end with the printed kit. A Playwright test proves the loop with no humans.

## Build

### 1. Host (`src/host/server.js`, `src/host/pacing.js`, `src/host/clients.js`)

- `node src/host/server.js <scenario.json> [--port 7331] [--stage2 <scenario.json>]`: resolves a relative scenario path against `process.env.INIT_CWD || process.cwd()` (so both `npm --prefix Monitor run host -- Data/...` from the repo root and `node Monitor/src/host/server.js Data/...` work), loads the scenario (WO-01 loader, validate first; refuse to start on problems), creates the sim, serves `web/` statically (`/plan.html`, `/site.html`, `/facilitator.html`, plus `/Voice/...` from the repo's `Voice/` folder for WAV lines if present), opens `ws` on `/ws`.
- Pacing: the sim always steps by `dt 0.01` (the same step as the headless run, so triggers land on the same ticks); at `full` one step every 50 ms (5 s per day), at `slow` one step every 200 ms (20 s per day); `paused` advances nothing. Starts paused until the facilitator sends `ctrl start`. With `NODE_ENV=test` the facilitator may send `ctrl {action:"fast"}` (one step every 2 ms) for the e2e.
- Clients: `hello` registers a seat; a second client on a taken seat is a `mirror` (gets `state`, its `cmd`s are nacked `"mirror"`). Broadcast `state` with the seat's view at 4 Hz and immediately after any accepted `cmd`. Deliver drained messages to the seats they name (`voice` and `event` carry `seats`; `report` goes to plan and facilitator; `result` to all; `inspection` to the requester).
- `ctrl load` swaps the scenario (for Stage 2); `ctrl reset` recreates the sim with the same scenario; `ctrl start|pause|resume`. When Stage 2 ends and `result.overlayPreviousStage` names a stage whose result the host holds from this process, include it as `previousRun`.
- Write a transcript (same shape as the headless one) to `Monitor/out/<stage>.<timestamp>.json` at `result`, for the research record.

### 2. Plan page (`web/plan.html`, one file, vanilla JS, SVG chart)

What it must show (and nothing it must not):
- **LOB chart**: x = stations 0 to 60+00 with zone bands and boundaries labelled; y = days 1 to `deadlineDay`. Planned lines per crew (three distinct line styles, labelled at the end, not colour-coded for status); holds as flat segments. Reported actual lines as stepped polylines up to the last report, ending in a small open marker with the ± band for today. Flags from Site as plain markers at their station with the day. The promised finish day and the deadline as horizontal rules with labels. No "ahead/behind" words; the lines are the message.
- **Plan editing**: in Stage 2 (or when `plan.locked` is false) drag a crew's first point vertically to set its start day (snaps to whole days); a Hold tool adds a flat segment from a chosen day with a day count; a Lend tool picks machine → crew → days; Order and Protect panels list the catalog with prices and lead days including this city's delay, and a station range for protection; Demob/Remob buttons per crew. In Stage 1 the editing tools show but return the host's nack text verbatim (for example "plan locked", "not in the budget") beside the Commit button; there is no other feedback.
- **Respond**: when `view.responses` is not empty, a panel lists the event's response options with their cost and (for `hire_excavator`) a machine picker; choosing one drafts a `pay` op. The P1 option "clear with your own excavator" is drafted through the Lend tool (exc's machine → pipe), and the panel says so in one line.
- **Draft and Commit**: a list of pending ops with their cost; one Commit button sends them as one `commit`. The world's `slow` state shows as a plain label "office time: 20 s per day" and `full` as "5 s per day"; no countdown bar, no urgency colour.
- **Budget strip**: budget, spent, committed, remaining, deadline day, today (display day). Numbers only.
- **Inbox**: dated items newest first; daily reports render as "Day 6: exc +220 ft (1,320), pipe +0 ft (720), back +250 ft (500); spend $31,200" with the scenario's notes.
- **Radio log**: every order with status (`sent`, `landed`, `confirmed`, `not carried out`) and a "Radio again" button on `not carried out`.
- **Keypad**: enter a permit code for a zone, enter an inspection number for a zone; the host's ack shows the permit number posted or the nack text verbatim. Nothing green, nothing red, no checkmark; a posted number is the whole confirmation.
- **Event cards**: facts from the host's `event` message when the Plan seat is in `seats` (rare); otherwise Plan learns by voice. PM voice lines: play `/Voice/<stage>/<lineId>.wav` if it exists (HEAD request once per line), else show the line's text in a "PM" box for 8 seconds.
- **End of stage**: when `result` arrives, replace the chart with the overlay: planned vs actual, Stage 1's lines faint beneath in Stage 2, the change log (every commit with its day), the numbers of the result as a table. Still facts only; the title is the stage name, not a grade.

### 3. 2D Site page (`web/site.html`)

A plan view of the line for the seat that has no headset, and the stand-in for the Quest app in Phase 0:
- A horizontal strip of 60 stations with zone boards; each station cell shows trench state (undug/open/piped/backfilled as hatch patterns), water and wall marks when `inspect`ed or when Site is within the zone, protection in place, crew icons at their live positions with a small mood glyph (0–3), machine plate text on hover.
- The **truck**: click a station to `moveTo`; a Dismount/Mount button; while moving, the truck icon slides and the buttons disable.
- **Inspect** buttons for the targets in `Docs/PROTOCOL.md`; the returned text appears on a clipboard panel (and is read aloud with `speechSynthesis` if available; it is optional).
- **Flag** (station + 40-char note), **Stop work** (current zone), **Confirm** list for orders landed at this station (Done / Not carried out), **Listen** (shows foremen lines when arguing or idle).
- **Trailer board** panel: live actual lines per crew (a mini LOB with no planned lines) and the permit numbers posted per zone. No plan, no money, no forecast percentage; the sky is a word and a drawing (`clear`, `towers to the south`, `rain`).
- Event cards: facts only, when Site is in `seats`.
- Works at phone width (one column, strip scrolls horizontally).

### 4. Facilitator page (`web/facilitator.html`)

Start / Pause / Resume / Reset, Load Stage 2, current `t` and display day, speed, the Plan view and Site view JSON side by side (collapsible), upcoming events and deviation states, a Download transcript button. Not for players.

### 5. E2E (`e2e/stage1.e2e.js`, `node:test` + Playwright)

Starts the host on a free port with `stage1_texas.json`, opens the three pages in one Chromium, then: facilitator Start; Site clicks station 7+20 and Dismount before Day 6; wait for the Site event card "Trench wall collapse at 7+20"; assert the Plan page has **no** element containing "collapse" at that moment and its newest inbox item is a daily report; Site Stop work; Plan drafts `lend` (exc's machine → pipe) + `hold back 2` and Commits; assert the speed label returns to "5 s per day"; Site moves to the excavator, Confirm → Not carried out (F1), Plan clicks Radio again, Site Confirm → Done; Site moves to the backfill crew, Confirm → Done; wait for the next `report`; assert Plan's reported pipe feet equals 720 for that day. At the argument (Site page shows two crews `arguing`), Plan commits `hold back 3`. Then speed-run (`ctrl fast`, test builds only) to the result and assert the overlay rendered, `finishDay` is above 35 and below 46, and no `lost`. Screenshot each page at 1280×800 into `Monitor/out/e2e/`. Finally, fetch every page's `document.body.innerText` and assert none of `correct|wrong|well done|good job|score|mistake|should have` appears.

