# WO-01 — Scenario and catalog loader + validator

## Goal

`node Monitor/src/scenario/validate.js Data/Scenarios/stage1_texas.json` loads a stage file against `Data/catalog.json`, checks every rule listed in `Docs/SCENARIO_SCHEMA.md` under "Validation", prints the `_validate` keys it found (path and text) so they can be handed to the construction-science validators, and exits 0; a broken file exits 1 with one line per problem. Later work orders import `loadScenario()` and never re-implement these checks.

## Read

- `AGENTS.md`
- `Docs/SCENARIO_SCHEMA.md` (whole)
- `Data/Scenarios/stage1_texas.json`, `Data/Scenarios/stage2_texas.json`, `Data/catalog.json` (read, do not edit)

## You may change

- `Monitor/src/scenario/**`, `Monitor/test/scenario*.test.js`, `Monitor/test/fixtures/**`

## Build

1. `src/scenario/load.js`: `loadScenario(path, { catalog })` → a frozen object with the file's data plus derived fields: `zoneOf(ft)`, `stations[]` (every 100 ft), `dailyFleetUsd` (sum of the crews' machine daily cost), `crewRate(crewId)`, `checkDigitOk(code)`. Strips nothing; `_`-prefixed keys stay but are ignored by logic.
2. `src/scenario/validate.js`: CLI and `validateScenario(scenario, catalog) → { ok, problems[], toValidate[] }`. Checks, each with a stable message id:
   - machine keys exist (`crews[].machine`); city exists in the catalog
   - zones tile `[0, lengthFt]` with no gap or overlap, ids 1..n in order
   - `startDay >= 1`; `promisedFinishDay < deadlineDay`; `budgetUsd > 0`
   - permit cards: one per zone, distinct codes, every code `dddd-c` with `c = (sum of digits) mod 10`; same for inspection card numbers
   - `permits.heldBy` in {pm, rules}; `openZoneLimit` in 1..zones
   - every event `trigger.crew` / `hits` is a crew id or `all`; `trigger.kind` in {crewReaches, day, zoneSigned}; `type` is one of the eight workbook codes; `options[].check.seat` in {site, plan, rules}; event `zone` consistent with `stationFt` when both set
   - every `deviations[].type` in F1..F5 and `when.kind` in the schema's list
   - every `lines[].trigger` in the schema's trigger list; `speaker` in the schema's list; ids unique
   - every `inbox[].day >= 1`
   - forbidden keys anywhere (case-insensitive): `whenRight`, `whenWrong`, `correct`, `verdict`, `score`
   - collect every `_validate`-style key (`_validate`, `_x_validate`) with its JSON path and text
3. Exit codes: 0 ok, 1 problems, 2 usage. Output: problems first, then `to validate (N):` list, then `OK <id>` or `FAIL <id>`.
4. Tests: both shipped stages validate OK with zero problems and list at least 2 `_validate` items each (the catalog's own `_validate` keys are listed separately, at least 6); fixtures in `test/fixtures/` that break each rule (one file per rule is fine, or one file with several breaks and assertions on the message ids); a wrong check digit is caught.

## Acceptance checks

```
npm --prefix Monitor test
node Monitor/src/scenario/validate.js Data/Scenarios/stage1_texas.json ; echo exit=$?      # exit=0, "OK stage1_texas", a "to validate" list
node Monitor/src/scenario/validate.js Data/Scenarios/stage2_texas.json ; echo exit=$?      # exit=0
node Monitor/src/scenario/validate.js Monitor/test/fixtures/bad_checkdigit.json ; echo exit=$?   # exit=1, mentions the bad code
git status --short            # only Monitor/src/scenario, Monitor/test
```

## Out of scope

No simulation, no changes to the data files (if you believe a data file is wrong, say so in NOTES with the path and the value; the orchestrator decides).
